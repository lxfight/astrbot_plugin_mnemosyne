# Architecture and Data Flow

Mnemosyne keeps conversation summarization, embedding, retrieval, and prompt injection inside the AstrBot plugin process. Local Chroma is the default backend, so the first deployment does not require a separate database service.

## Components

| Component | Responsibility |
| --- | --- |
| `main.py` | Registers the plugin and initializes providers, storage, the admin panel, and message hooks. |
| `memory_manager/context_manager.py` | Maintains conversation context and long-term-memory placement. |
| `memory_manager/message_counter.py` | Counts conversation turns and triggers summarization. |
| `core/memory_operations.py` | Implements summary storage, vector search, filtering, reranking, and injection. |
| `memory_manager/vector_db/` | Provides one adapter interface for Chroma, Milvus, Qdrant, and Weaviate. |
| `admin_panel/` and `web_api.py` | Expose statistics, search, editing, deletion, and runtime-status APIs. |

## Write Path

```text
Conversation messages
  -> message count reaches num_pairs
  -> LLM summary
  -> Embedding Provider generates a vector
  -> vector database insert
  -> flush when supported by the backend
```

Summarization runs as a background task. If the insert succeeds but flush fails, the memory remains valid and becomes visible asynchronously, so Mnemosyne does not report a failed write or trigger a duplicate. A failed insert rolls the session counter back so the next turn can retry summarization.

## Read Path

```text
LLM request
  -> check memory_injection_interval
  -> embed the user query
  -> vector similarity search
  -> session/persona/participant filters and reranking
  -> inject memories with an explicit data-boundary notice
```

When there are no rerankable keywords and participant filtering is disabled, the candidate count is exactly `top_k`. Otherwise Mnemosyne expands it to `min(top_k * 4, 60)`. Only the final `top_k` records enter the prompt.

Injected text is explicitly marked as historical reference data rather than instructions, reducing the risk that memory content is treated as a system request or tool call.

## Data Model

| Field | Type | Purpose |
| --- | --- | --- |
| `memory_id` | INT64 auto primary key | Memory record ID. |
| `personality_id` | VARCHAR(256) | Associated persona ID. |
| `session_id` | VARCHAR(500) | Session scope for isolation and filtering. |
| `content` | VARCHAR(4096) | Summarized memory text. |
| `embedding` | FLOAT_VECTOR | Vector generated by the active Embedding Provider. |
| `create_time` | INT64 | Unix timestamp used for filtering and display. |

The embedding model determines vector dimensions. After changing models, run `/memory init --force` to validate or rebuild the collection.

## Backend Abstraction

Every backend implements the same connection, collection initialization, insert, search, query, delete, and flush operations. The business layer does not depend on a specific database SDK, so switching backends only requires configuration changes and initialization in the new backend.

Records are not migrated automatically between backends. A cross-backend migration must export the old records, regenerate embeddings, and write them into the new collection.

## Observability

The plugin process keeps staged latency and API success metrics, and the admin panel reads the same collector. Slow-query thresholds cover Embedding, vector search, post-processing, injection, database operations, and the complete retrieval flow so operators can separate provider network time, backend cost, and local CPU work.
